# BSAA — Feature Inventory

This document describes what is **actually implemented and working** in the codebase today, verified by reading every agent, adapter, analyst, and report generator, and by running the test suite. It intentionally omits anything aspirational — see `OVERVIEW.md` for the narrative pitch and its honest caveats.

Verified against commit `4cff3e3` (`feat: replace verdict/composite score with flag-severity counts + Summary tabs`).

## What's supported today vs planned

| Dimension | Status |
|---|---|
| **Bank coverage (PDF)** | HDFC and ICICI only. Bank is detected from page-1 header text; any other bank raises `AdapterError` rather than silently extracting 0 rows. Column layouts are hardcoded per bank in `adapters/digital_pdf.py` and `pipeline/normaliser.py` — there is no per-bank YAML profile system (the `profiles/` directory exists but is empty) and no LLM fallback for unrecognised layouts, despite earlier design notes describing one. |
| **Bank coverage (CSV / Excel)** | Bank-agnostic by construction — columns are matched by header keyword (`Date`, `Debit`/`Withdrawal`, `Credit`/`Deposit`, `Balance`, …), so any bank's CSV/Excel export works as long as it has a recognisable header row. Not tested against real non-HDFC/ICICI exports. |
| **Bank coverage (scanned PDF / image)** | Also bank-agnostic — OCR + generic date/amount regex, no bank-specific parsing. Accuracy depends entirely on OCR quality (Tesseract); no gold-set accuracy numbers exist for this path. |
| **Input formats** | Digital PDF, scanned/image-only PDF (OCR), single JPG/PNG image, CSV, Excel (.xlsx/.xls, multi-sheet, merged cells). All five have adapters and unit tests. |
| **Jurisdictions** | India only. Six compliance rules (§269ST, GST, TDS, PMLA, related-party concentration, §269SS/§269T). The module is pluggable in principle (`jurisdictions.JurisdictionModule` protocol) but only one jurisdiction is implemented. |
| **Validation gating** | The validator's result **does gate the pipeline**: both `pipeline/orchestrator.py` and `demo/pipeline_runner.py` raise `ValidationFailedError` and stop before categorisation if any check returns an ERROR-severity issue (balance break or duplicate transaction ID). Verified by `tests/test_validation_gating.py`. |
| **Accuracy validation** | 100% synthetic. The 22-statement "gold set" (`data/gold/`) is entirely generated by this project's own synthetic generator (`tools/synthetic_gen.py`). `data/real_anonymised/` exists as a directory but is empty — no accuracy number anywhere in this project has been validated against a real bank statement. |
| **Current regression numbers** (synthetic gold set, 22 statements, run 2026-07-26) | Extraction **100%** (target 88% ✅) · Categorisation **99.8%** (target 88% ✅) · Compliance recall **100%**, n=2 statements (target 90% ✅, small sample) · **Risk recall 73.3%**, n=5 statements (target 85% ❌) · **Customer-ID clustering accuracy 82.3%**, 52,946 pairs (target 90% ❌) · Reconciliation recall: not measured, no ground-truth fixture exists yet. |
| **Unit test suite** (`make test`) | 909 tests collected, **908 passed, 1 failed**. The failure (`test_vc_lens.py::TestEdgeCases::test_generate_is_idempotent`) is a byte-length mismatch between two `.xlsx` outputs generated moments apart — almost certainly an embedded timestamp in the zip container's `docProps` metadata, not a logic defect; the two workbooks were not compared cell-by-cell to fully rule out a real non-determinism. |

## Layer 1 — Ingestion

Format adapters. Each adapter's only job is to extract raw rows in bank-native string form — none of them interpret amounts, dates, or categories. All five live in `adapters/`.

### Digital PDF adapter (`adapters/digital_pdf.py`)
- **What it does:** Extracts transaction tables from digital (text-layer) HDFC and ICICI statement PDFs using `pdfplumber`.
- **Inputs:** A PDF file path. **Outputs:** `RawStatement` (bank name, account id, period, opening balance, list of `RawRow`).
- **Specifics:** Detects the bank from the first 300 characters of page 1 (falls back to scanning all pages); hardcoded column-index maps for HDFC's 7-column and ICICI's 8-column layouts; skips repeated header rows across pages and "opening/closing balance" metadata rows; regex-extracts account number, statement period, and opening balance from page text (not the table).
- **Type:** Deterministic.
- **Limitations:** Only HDFC and ICICI are recognised — any other bank raises `AdapterError` with an explicit message rather than silently returning 0 transactions. No LLM fallback and no per-bank profile files exist yet.

### CSV adapter (`adapters/csv.py`)
- **What it does:** Extracts rows from any bank's CSV export.
- **Inputs:** CSV file path. **Outputs:** `RawStatement` (bank name always `"UNKNOWN"`).
- **Specifics:** Auto-detects delimiter (`,`, `;`, tab, `|`) via `csv.Sniffer`; tries `utf-8-sig`/`utf-8`/`cp1252` encodings in order; scans up to 20 rows for a header containing Date + Debit + Credit + Balance keywords (handles title/metadata rows before the real header); shares column-keyword matching logic with the Excel adapter (`adapters/_column_mapping.py`).
- **Type:** Deterministic.
- **Limitations:** Requires a header row with recognisable keywords; if none of the first 20 rows qualifies, raises `AdapterError`.

### Excel adapter (`adapters/excel.py`)
- **What it does:** Extracts rows from `.xlsx`/`.xls` bank exports.
- **Inputs:** Excel file path. **Outputs:** `RawStatement`.
- **Specifics:** Scores every sheet in a multi-sheet workbook by header match quality and picks the best one; resolves merged cells (openpyxl only stores a value in the top-left cell of a merge) before header/row matching; same column-keyword matching as the CSV adapter.
- **Type:** Deterministic.

### Scanned PDF adapter (`adapters/scanned_pdf.py`)
- **What it does:** OCRs image-only (non-digital) PDF statements.
- **Inputs:** PDF file path. **Outputs:** `RawStatement`, with per-row `ocr_confidence` (0–100).
- **Specifics:** Renders each page at 300 DPI via `pdfplumber`; preprocesses with greyscale → deskew (±5°, variance-of-row-sums scoring) → median-filter denoise → Otsu binarisation (implemented from scratch on the histogram, no OpenCV dependency); runs Tesseract with word-level bounding boxes and confidence; groups words into lines using Tesseract's block/paragraph/line numbering; parses each line by taking the *last two* amount-like tokens as (transaction amount, balance) and infers debit-vs-credit from the change in running balance rather than column position, since OCR silently drops empty cells.
- **Type:** Deterministic (no ML classification — Tesseract is OCR, not an LLM).
- **Limitations:** Requires the Tesseract binary on `PATH`; accuracy is entirely dependent on scan/photo quality; no gold-set numbers exist for this path since the gold set is all digital PDFs.

### Image adapter (`adapters/image.py`)
- **What it does:** Thin wrapper treating a single JPG/PNG as a one-page scanned statement, reusing the scanned-PDF OCR pipeline.
- **Type:** Deterministic.

## Layer 2 — Normalisation

### Normaliser (`pipeline/normaliser.py`)
- **What it does:** Converts a `RawStatement` (bank-native strings) into a `StatementDocument` of `CanonicalTransaction` objects.
- **Inputs:** `RawStatement`. **Outputs:** `StatementDocument` with `validation_status=UNVALIDATED`.
- **Specifics:** Per-bank date-format tables (HDFC `DD/MM/YY`, ICICI `DD-MM-YYYY`, generic fallback list for CSV/Excel/OCR sources); Indian-format amount parsing (strips commas); deterministic `transaction_id` = `"txn_" + SHA-1(file stem, page, row, date, amount)[:10]`, stable across reruns; derives the statement period from transaction dates if the header regex didn't find one; unparseable rows are silently skipped (the Validator's `SPARSE_TRANSACTIONS` check is the backstop that would catch a systematic extraction gap).
- **Type:** Deterministic. **Note:** despite earlier design notes describing a "per-bank YAML profile" system with an LLM fallback for unknown layouts, the current implementation is a hardcoded Python format table with no YAML files and no LLM involved anywhere in normalisation.

### Validator (`pipeline/validator.py`)
- **What it does:** Audits a `StatementDocument` for data-quality issues and sets `validation_status` to `PASSED` or `FAILED`.
- **Inputs:** `StatementDocument`. **Outputs:** `ValidationReport` (list of issues + counts) and a mutated `doc.validation_status`.
- **The six checks:**
  1. **BALANCE_BREAK** (ERROR) — `prev.balance + credit − debit == curr.balance`, ±₹1 tolerance, checked in physical PDF order (page, row), not date order.
  2. **DUPLICATE_ID** (ERROR) — two transactions share a `transaction_id`.
  3. **SPARSE_TRANSACTIONS** (WARNING) — fewer than ~0.5 transactions/week for the stated period.
  4. **OUT_OF_ORDER** (WARNING) — a transaction's date is earlier than the previous one in PDF order.
  5. **DATE_OUTSIDE_PERIOD** (WARNING) — transaction date falls outside the statement period (±2-day buffer).
  6. **EMPTY_DESCRIPTION** (WARNING) — blank transaction description.
- **Gating:** Any ERROR-severity issue (checks 1–2) sets `validation_status=FAILED`. Both `pipeline/orchestrator.py` and `demo/pipeline_runner.py` raise `ValidationFailedError` immediately after validation and never call the categoriser or any downstream analyst on a failed document — confirmed by `tests/test_validation_gating.py`, including a batch-isolation test showing one bad statement doesn't affect the rest of a cohort.
- **Type:** Deterministic.

## Layer 3 — Enrichment

### Categoriser (`analysis/categoriser.py`)
- **What it does:** Assigns one of ten `TransactionCategory` values to every transaction.
- **Inputs:** `StatementDocument`. **Outputs:** mutated `doc` + `CategorisationStats` (rule/LLM/fallback counts).
- **Specifics:** Ordered regex rule list (first match wins) covering salary/payroll/wages, GST/TDS/professional-tax/ESI/PF, founder/director withdrawals, bank fees/penalties, loans in/out, self-transfers, invoice-referenced and cash/UPI/POS/Razorpay revenue credits, and catch-all revenue/vendor-payment rules for anything left over. Unmatched transactions (none, in practice — the catch-alls guarantee every transaction matches) fall through to a batched Claude Haiku call (up to 50 transactions/request) constrained to the same 10-category vocabulary; disabled gracefully (falls back to rule result / `OTHER`) if `ANTHROPIC_API_KEY` is absent or the call fails.
- **Type:** Hybrid (deterministic rules first, LLM fallback). On the gold set, measured categorisation accuracy is 99.8% (rule layer alone, since the regression suite runs rule-only for determinism).

### Related-party tagger (`pipeline/related_party.py`)
- **What it does:** Flags transactions involving a user-supplied list of affiliates (directors, related companies, etc.).
- **Inputs:** `StatementDocument` + `list[Affiliate]`. **Outputs:** mutated `doc` (`is_related_party`, `related_party_match`, `counterparty` populated on every transaction, not just matches).
- **Specifics:** Stage 1 (deterministic) strips payment prefixes (NEFT/RTGS/IMPS/UPI…), IFSC routing codes, trailing reference/invoice tokens, opaque bank-ref codes, and legal-form suffixes (Pvt Ltd, LLP, …) before exact-matching against affiliate names/aliases. Stage 2 (optional) asks Claude Haiku, batched 30 at a time, whether an unmatched cleaned description plausibly refers to a known affiliate (confidence ≥ 0.8 required to accept).
- **Type:** Hybrid.

### Customer identity resolver (`pipeline/customer_identity.py`)
- **What it does:** Groups REVENUE transactions into distinct customers so churn/NRR/concentration can be computed.
- **Inputs:** `StatementDocument`. **Outputs:** mutated `doc` (`customer_id` populated on REVENUE transactions).
- **Specifics — three stages:** (1) reuse the related-party tagger's name-cleaning to get a canonical counterparty string; (2) exact-match clustering — `customer_id = "cust_" + SHA-1(name)[:10]`; (3) optional embedding merge (`sentence-transformers`, `all-MiniLM-L6-v2`) via union-find, merging clusters with cosine similarity > 0.85, cached to `.cache/embeddings.json`.
- **Aggregator awareness (the flagship fix):** Transactions whose description matches a known payment-aggregator pattern (Razorpay, Cashfree, PayU, Paytm, PhonePe, Instamojo, CCAvenue, BillDesk, Pine Labs, Juspay, EBS, Atom Technologies, Worldline) are **excluded from clustering entirely** and tagged with an `aggregator_settlement` anomaly flag instead of a `customer_id` — because a settlement line is a lump-sum payout for many end-customers, not one customer, and clustering it under one name would fabricate a fake "customer" with implausibly steady revenue and zero churn.
- **Type:** Hybrid (embedding stage optional/off by default in the demo pipeline; exact-match + aggregator exclusion always run).
- **Limitations:** Measured pairwise clustering accuracy on the gold set is 82.3% against a 90% target (currently failing the regression suite).

## Layer 4 — Analysis

### Financial-health analyst (`analysis/financial_analyst.py`)
- **What it does:** Pure arithmetic on categorised transactions — burn, runway, growth, concentration.
- **Inputs:** `StatementDocument`. **Outputs:** `FinancialMetrics`.
- **Computes:** total/average monthly revenue and burn (burn = VENDOR_PAYMENT + SALARY + TAX + FEES + FOUNDER_WITHDRAWAL + LOAN_OUT); runway = closing balance ÷ average monthly burn (`None` if profitable); month-over-month revenue growth rates and their average; customer-revenue HHI and top-customer revenue share (only when `customer_id` is populated).
- **Type:** Deterministic.

### Risk / red-flag analyst (`analysis/risk.py`) — six detectors
- **What it does:** Runs six independent pattern detectors and produces a `RiskReport` (flags + composite score + narrative).
- **Inputs:** `StatementDocument` (+ optional declared founder salary). **Outputs:** `RiskReport`.
- **The six detectors:**
  1. **`structuring`** — ≥4 credits between ₹1.5L–₹2L within a 7-day window (possible §269ST evasion via splitting).
  2. **`round_tripping`** — an outflow and a same-counterparty inflow within 3–14 days, amounts within 5%.
  3. **`spike_drain`** — a month's net cash flow deviates >2.5σ from a leave-one-out baseline of the other months (requires ≥3 months of data).
  4. **`customer_concentration`** — top-3 customers exceed 60% (MEDIUM) or 80% (HIGH) of revenue.
  5. **`round_amount_clustering`** — >30% (MEDIUM) or >60% (HIGH) of revenue transactions are exact ₹1,000 multiples.
  6. **`founder_over_extraction`** — `FOUNDER_WITHDRAWAL` in a month exceeds 3× declared salary (HIGH), or ₹5L/month with no declared salary on file (MEDIUM).
- **Composite score:** weighted sum (HIGH=10, MEDIUM=5, LOW=2), capped at 100. Exposed as `compute_composite_score()` so callers that rebuild the flag list (e.g. Workbench's fund-specific detector toggles) recompute it consistently.
- **Narrative:** Claude Haiku 3–5 sentence summary of the flags, with a deterministic fallback narrative when no API key is set.
- **Type:** Hybrid (deterministic detectors + LLM narrative layer only).
- **Limitations:** Measured risk recall on the gold set is 73.3% against an 85% target (currently failing the regression suite; n=5 statements with an eligible injected flag).

### Customer analytics analyst (`analysis/customer_analytics.py`)
- **What it does:** Derives customer-level behaviour metrics from REVENUE transactions with a resolved `customer_id`.
- **Inputs:** `StatementDocument`. **Outputs:** `CustomerAnalyticsReport`.
- **Metrics:**
  - **Monthly active customers** + linear-regression trend slope.
  - **Churn events** — a customer is churned once their last active month is ≥3 months before the final month in the data (guarantees 3 confirmed silent months). **Structurally cannot fire on statements shorter than 4 months** — this is a real, current limitation, not a bug: with fewer months there's no way to confirm 3 months of silence.
  - **NRR (net revenue retention)**, per consecutive month pair — cohort of customers active in month M, their combined revenue in M+1 ÷ their revenue in M. Reported **as a per-period ratio, not annualised** (an earlier version raised a single month's ratio to the 12th power, which is no longer done).
  - **Cohort retention** — for each first-payment cohort, the fraction still paying at each subsequent month offset.
  - **Concentration trajectory** — top-3 and top-10 customer revenue share, per month.
  - **Payment regularity alerts** — customers with ≥6 active months whose most recent payment gap exceeds 2× their historical median gap.
  - **Aggregator revenue share** (`aggregator_revenue_pct`) and an `is_aggregator_dominated` flag (≥30% of revenue is aggregator-settled) — surfaced to every report lens via `aggregator_caveat_text()`.
- **Type:** Deterministic.
- **Limitations:** Churn/NRR/cohort metrics need ≥4 months of statement history to produce anything; on shorter windows they report empty, not "insufficient data" (a UI/reporting nuance to be aware of, not a crash). Aggregator-dominated statements correctly suppress misleading customer counts but genuinely cannot see the underlying customers — this is a hard limit of bank-statement data, not a solvable bug.

### Financial health alerts (`analysis/financial_health_alerts.py`)
- **What it does:** Converts `FinancialMetrics` + `CustomerAnalyticsReport` into investor-facing alerts, and is the **single shared source of every band threshold** (runway/burn/NRR/churn/concentration) used by all four report lenses — no lens re-implements its own cut points.
- **Inputs:** `FinancialMetrics`, `CustomerAnalyticsReport`. **Outputs:** `FinancialHealthReport` (list of `HealthAlert`).
- **Ten detectors:** critical/low/short runway, extreme/high burn-to-revenue ratio, sustained/2-month revenue decline and stagnation, burn accelerating faster than revenue, consistently cash-negative months, severe/contraction/below-par NRR, high/elevated churn, shrinking customer base (3 consecutive months), high/moderate customer concentration, aggregator-dominated revenue.
- **Type:** Hybrid (rule-based detection; descriptions optionally polished by one batched Claude Haiku call; rule-based text used as fallback).
- **Note:** this was a known architectural gap in an earlier version (only fed the Streamlit demo, not the exportable reports) — it is now consumed by the Angel and VC lenses directly; the Workbench lens still computes its risk-flag view independently (via `workbench_config.py`) though its Customer Master sheet has been fixed to reuse `customer_analytics.py`'s own active-customer data rather than re-deriving it from raw transactions.

### Compliance analyst (`analysis/compliance.py` + `jurisdictions/india/rules.py`)
- **What it does:** Runs a jurisdiction's compliance rule set against a statement.
- **Inputs:** `StatementDocument` + a `JurisdictionModule`. **Outputs:** `ComplianceReport` (exceptions + severity counts).
- **The six India rules, each with citation:**
  1. **§269ST Cash Transaction Limit** (Income Tax Act, 1961 §269ST, HIGH) — cash credits ≥₹2L from one party in one day.
  2. **GST Payment Consistency** (CGST Act, 2017 §39, MEDIUM) — months with revenue >₹3L but no GST-pattern debit, once annualised revenue exceeds the ₹40L registration gate. Explicitly labelled in its own description as *"a payment-pattern heuristic, not a statutory determination of GST non-compliance."*
  3. **TDS Disbursement Pattern** (Income Tax Act §192/§194A/§194C, MEDIUM) — salary outflow annualises above ₹5L with no TDS-pattern debit found.
  4. **High-Value Cash Aggregation** (PMLA Rules 2005 Rule 3(1)(a), HIGH) — ≥₹10L cash activity in any rolling 30-day window. Labelled *"a cash-volume heuristic, not a statutory STR determination."*
  5. **Related-Party Transaction Concentration** (Companies Act §188 governance principle, MEDIUM) — related-party debits exceed 20% of total debits. Labelled *"a concentration heuristic, not a statutory §188 determination (which requires net-worth data not available from a bank statement alone)."*
  6. **§269SS/§269T Cash Loan Prohibition** (Income Tax Act §269SS/§269T, HIGH) — cash loan/deposit ≥₹20,000.
- **Investor framing:** each exception carries both a technical description and an `investor_risk_framing` sentence, optionally rewritten by a single batched Claude Haiku call.
- **Type:** Hybrid (deterministic rule evaluation; optional LLM prose polish).
- **Limitations:** heuristics run against bank-statement data alone — several rules explicitly disclose in their own description text that they are not a substitute for legal/statutory determination. Only one jurisdiction (India) is implemented. Measured compliance recall on the gold set is 100%, but on only 2 statements with an eligible injected compliance flag — too small a sample to treat as a strong accuracy claim.

### Reconciliation analyst (`analysis/reconciliation.py`)
- **What it does:** Cross-checks a company's self-reported claims (from a pitch deck or manual input) against what the bank statement actually shows.
- **Inputs:** `StatementDocument`, `CompanyClaims` (optional — returns an empty, `claims_provided=False` report if not supplied), `CustomerAnalyticsReport`, `FinancialMetrics`. **Outputs:** `ReconciliationReport`.
- **The five checks:** total revenue, active customer count, NRR, a "we've never lost a customer" claim against detected churn events, and salary spend vs. declared headcount × average salary. Each produces a `MismatchDirection` (over/under-reported), a severity banded by deviation magnitude, and an investor framing sentence (LLM-polished when available).
- **Type:** Hybrid.
- **Note:** zero-actual-value edge cases (e.g. claimed revenue exists but the bank shows none at all) are handled as an explicit HIGH-severity finding rather than being silently masked by a percentage calculation that divides by zero. The salary-vs-headcount check's over/under-reported direction is verified correct in the current code (actual bank spend is the base, declared-implied spend is compared against it).
- **Limitations:** No ground-truth fixture exists for measuring reconciliation recall — the gold set has no paired "declared claims with a known intentional mismatch," so this metric is explicitly reported as "not measured," not a fabricated number.

## Layer 5 — Output (four lenses + shared narrative)

All four lenses are pure presentation — they read from `FinancialMetrics`, `RiskReport`, `CustomerAnalyticsReport`, `ComplianceReport`, `ReconciliationReport`, `FinancialHealthReport` and format them; none contain analysis logic of their own. None of the four renders an investment verdict, recommendation, or star rating — this is a deliberate, tested product decision (`tests/test_vc_lens.py::TestNoVerdictOrScore`, mirrored across lenses): the tool surfaces evidence and counts, the reader forms their own judgment.

### Angel Lens (`reports/angel_lens.py`)
- **What it is:** A 1-page A4 PDF (ReportLab) for angel investors.
- **Contents:** header/company/period → one-paragraph Summary (shared narrative engine) → flag-severity count table (risk flags + health alerts, by HIGH/MEDIUM/LOW — replaces a previously-removed composite score/verdict banner) → KPI row (Revenue, Burn, Runway, MoM Growth) → up to 6 months of Revenue/Burn/Net table → 6–8 "Investor Health Signals" bullets (financial + customer + risk, each ✓/!/!! marked) → disclaimer footer.

### VC Lens (`reports/vc_lens.py`)
- **What it is:** A 6-sheet XLSX workbook + 3-page PDF summary for institutional investors.
- **Sheets:** Summary, Financial Health, Red Flags, Customer Analytics, All Transactions, Related Parties.
- **Notably:** surfaces the aggregator-dominance caveat directly in the Customer Analytics sheet and PDF page 2 when applicable; the Summary sheet/PDF never uses "clean" without qualification (tested explicitly).

### Workbench Lens (`reports/workbench_lens.py`)
- **What it is:** The deepest report — a 10-sheet XLSX + 4-page PDF for in-house fund analysts.
- **Sheets:** Executive Summary, Financial Health, Risk Flags, Customer Analytics, Compliance Findings, Reconciliation, All Transactions, Related Parties, Customer Master, Raw Data Export.
- **Fund customisation (`workbench_config.py`):** any of the six risk detectors can be toggled off per fund, and custom fund-specific detector functions (`(StatementDocument) -> list[Flag]`) can be registered and composited into the same score — no changes to `analysis/risk.py` required.
- **Customer Master sheet:** derives each customer's Active/Churned/Inactive status from `CustomerAnalyticsAnalyst`'s own computed `active_customer_ids_by_month` and `churn_events`, not by re-deriving churn logic from raw transactions a second time.

### Network Lens (`reports/network_lens.py`)
- **What it is:** A cross-company comparison workbook + PDF for angel networks and portfolio-level review — the only lens that operates on a *list* of already-analysed companies rather than one.
- **Sheets:** Comparison (sortable Excel table), Risk & Compliance Detail (the actual flags/exceptions behind each company's counts, not just the totals), Risk Distribution, Sector Breakdown, Company Reports (links back to each company's own lens report).
- **Portfolio narrative (`analysis/portfolio_narrative.py`):** a cross-company Claude Haiku synthesis (4–6 sentences: common risk themes, companies of greatest concern named explicitly, compliance issues, one recommendation), with a rule-based fallback.

### Shared narrative engine (`analysis/report_narrative.py`)
- **What it does:** Produces the one-paragraph "Summary" text reused by the Angel, VC, and Workbench lenses (and `severity_counts()`, the shared flag/alert/exception counting helper used by every lens and the demo UI).
- **Type:** LLM (Claude Haiku) with a fully deterministic rule-based fallback. System prompt explicitly instructs it never to render an investment verdict or rating.

## Orchestration, versioning, batch processing

### Orchestrator (`pipeline/orchestrator.py`)
- A minimal Sprint-1-scope pipeline (adapter → normaliser → validator → categoriser → financial analyst), PDF-only, HDFC/ICICI-only. Raises `ValidationFailedError` on failed validation. This is **not** what the demo/regression/batch paths use.

### Demo pipeline runner (`demo/pipeline_runner.py`)
- The actual full pipeline used by the Streamlit demo, the regression suite, and batch processing: adapter → normaliser → validator → categoriser → related-party tagger → customer identity resolver → risk analyst → customer analytics → financial health alerts → compliance → reconciliation → all four report generators. PDF input only (HDFC/ICICI) at this entry point.

### Versioning (`pipeline/versioning.py`)
- Every run is tagged with the frozen schema version (read from `schema/CHANGELOG.md`) and a semver per agent (`AGENT_VERSIONS` dict). `ResultStore` persists a flattened result summary to `.pipeline_state/{run_id}/run.json`, indexed by input-content-hash so re-running the same file under a newer agent version creates a new record rather than overwriting history. `replay()` re-runs a past input's original file through the *current* code; `diff_results()` does a field-by-field diff between two stored runs.

### Batch processing (`pipeline/batch.py`)
- `BatchOrchestrator` runs the full pipeline over many inputs concurrently (default concurrency 4) using `asyncio.to_thread` + a semaphore (real concurrency comes from worker threads, since the pipeline itself is CPU-bound and makes blocking LLM HTTP calls, not from async I/O). A failure on one input is captured as an `Exception` value in the result dict, never raised — one bad statement cannot take down the rest of a batch (tested with a monkeypatched pipeline function in `tests/test_validation_gating.py::TestBatchIsolatesValidationFailure`).

## Cross-cutting: what changed since the last review

For anyone comparing against an older review of this codebase, the following previously-open issues are now fixed and verified in this pass:
- Validator gates the pipeline (previously it set a status field nobody checked).
- NRR is a period-over-period ratio, not a single month raised to the 12th power.
- Customer identity resolver excludes payment-aggregator settlements from clustering instead of fabricating a fake customer.
- Reconciliation's zero-actual-value division bug and the salary/headcount swapped-argument bug are both fixed.
- The gold-set regression harness runs the real Sprint 1–3 pipeline end-to-end (not a Sprint-1-only stub) and computes real risk/compliance/customer-ID accuracy numbers.
- Compliance rule descriptions now explicitly disclose "heuristic, not statutory determination" where the underlying signal can't actually establish a legal violation from bank data alone.
- The composite risk score / INVESTABLE-MONITOR-CAUTION verdict banner has been removed from all lenses in favour of flag-severity counts — tested explicitly (`TestNoVerdictOrScore`).
- Cross-lens threshold consistency: all bands (runway/burn/NRR/churn/concentration) are now defined once in `analysis/financial_health_alerts.py` and imported everywhere, tested in `tests/test_lens_consistency.py`.

Still open, confirmed in this pass:
- Risk-flag recall (73.3%) and customer-ID clustering accuracy (82.3%) are below their own regression targets on the synthetic gold set.
- No real-bank-statement validation exists anywhere in the project.
- PDF ingestion is HDFC/ICICI only; no YAML profile system or LLM fallback exists for other banks.
- The Workbench lens's risk-flag view is still computed via its own path (`workbench_config.py`) rather than sharing `financial_health_alerts.py` with the other lenses (though its Customer Master sheet has been fixed to reuse `customer_analytics.py`'s data).
