# BSAA — Bank Statement Analysis Agent: Project Overview

## 1. The problem

Every early-stage investment decision in India — an angel writing a ₹20L check, a network syndicating a seed round across a dozen members, a VC associate doing first-pass diligence on fifteen companies a quarter, or an in-house fund analyst building the memo that goes to an investment committee — eventually runs into the same unglamorous bottleneck: someone has to read the company's bank statements.

Pitch decks show ARR. Bank statements show cash. The gap between the two is where the real risk lives — inflated revenue, founder self-dealing, customer concentration nobody mentioned, a burn rate that doesn't match the "18 months of runway" slide, or simply a business that's quietly cash-negative every single month. Reading that gap by hand means opening a PDF, scrolling through hundreds of rows of narration text in bank-specific formats, manually categorising every transaction, doing the arithmetic for burn and runway, trying to spot patterns like structuring or round-tripping by eye, and cross-referencing whatever the company claimed in its data room. It is slow, it doesn't scale past a handful of deals a month, and it is inconsistent — two analysts reading the same statement will flag different things, and the same analyst reading it twice, a week apart, may not either.

The people who feel this most acutely are exactly the four groups BSAA is built for: angel investors who don't have a finance team and need a fast, honest read before wiring money; angel networks that need to compare many portfolio companies on the same footing; VCs and their associates who need institutional-grade rigor across a portfolio; and in-house fund analysts who need the deepest drill-down, with room to bolt on fund-specific rules.

## 2. The core insight — one engine, many lenses

The naive way to serve four different users is to build four different tools. BSAA instead separates the problem into two layers that almost never change together: **analysis** (what does this statement actually show?) and **presentation** (how should that finding be shown to this particular reader?). One pipeline — ingestion, validation, categorisation, enrichment, and five analysis engines — runs exactly once per statement and produces a single, shared set of findings: financial metrics, risk flags, customer analytics, compliance exceptions, reconciliation findings. Four lightweight "lens" report generators then read from that *same* set of findings and format it differently: a one-page PDF for an angel who wants the headline in ninety seconds, a six-sheet workbook for a VC associate who wants to build a model on top of it, a ten-sheet workbench for a fund analyst who wants every transaction and the ability to add custom detectors, and a cross-company comparison workbook for a network sizing up its whole portfolio at once.

This matters for two reasons beyond convenience. First, it means the four report types can never quietly disagree with each other — if the same statement shows an NRR of 80%, every lens classifies that as the same severity band, because all four read from one shared threshold table (`analysis/financial_health_alerts.py`) instead of each reimplementing its own cut points. Second, it means adding a fifth user type later — a lender doing asset-based lending diligence, say — is a new presentation template, not a new analysis engine. The hard part of the problem (does this statement show structuring, is revenue really growing, is the company burning faster than it earns) gets solved once and reused everywhere.

## 3. How a statement moves through the system

A user uploads a PDF, CSV, Excel file, or a photographed statement page. What happens next is five layers, each one handing a progressively richer object to the next.

**Layer 1 — Ingestion.** A format-specific adapter extracts every transaction row in its original, bank-native form — dates as the bank wrote them, amounts with commas, descriptions untouched — and does nothing else. It does not decide what a transaction *means*; it only gets the raw rows out of the file. Today this works reliably for HDFC and ICICI digital PDFs (bank-specific column layouts, detected from the header text), and works in a bank-agnostic way for CSV and Excel exports (columns matched by header keyword, so any bank's spreadsheet export works if it has a recognisable Date/Debit/Credit/Balance header) and for scanned PDFs or photographed pages (OCR via Tesseract, with debit/credit direction inferred from the change in running balance rather than column position, since OCR silently drops empty cells).

**Layer 2 — Normalisation.** The Normaliser converts those bank-native strings into the canonical schema every downstream agent shares: a `CanonicalTransaction` with a stable ID, a parsed date, a `Decimal` amount, and a `SourceReference` pointing back to the exact page and row it came from in the original file — so any finding, three layers later, can be traced back to the specific line that produced it. Immediately after, the Validator runs six integrity checks — balance continuity being the most important one, since it catches both extraction errors and doctored statements — and this is the one gate in the whole system that actually stops the pipeline: if the running balance doesn't reconcile, or if transaction IDs collide, the pipeline raises rather than silently producing a report on data it can't trust. Lower-severity issues (sparse transaction density, out-of-order dates, dates outside the stated period, blank descriptions) are recorded as warnings but don't halt anything.

**Layer 3 — Enrichment.** Three agents add structure without doing analysis yet. The Categoriser assigns each transaction one of ten categories (Revenue, Salary, Vendor Payment, Tax, and so on) using an ordered set of regex rules tuned to Indian bank narration conventions, falling back to a constrained Claude Haiku call for anything the rules don't resolve. The Related-Party Tagger checks transaction descriptions against a user-supplied list of affiliates — directors, related companies — first by exact match after stripping payment-system noise, then by an optional LLM fuzzy match for name variations. The Customer Identity Resolver is the one that makes customer-level analytics possible at all: it groups REVENUE transactions into distinct customers by canonical name, with an optional embedding-similarity merge step for near-duplicate names. Its most important behavior is what it deliberately *doesn't* do: transactions that look like a payment-aggregator settlement (Razorpay, Cashfree, PayU, and a dozen others) are excluded from customer clustering entirely, because a single settlement line is a lump-sum payout covering however many end-customers paid that day — treating it as one customer would fabricate a fake account with implausibly steady revenue and zero churn. Those transactions are flagged instead, and every downstream customer-analytics number discloses what share of revenue they represent.

**Layer 4 — Analysis.** Five analysts run over the enriched statement, each producing a self-contained report: financial health (burn, runway, revenue trend, customer concentration — pure arithmetic), risk (six independent pattern detectors described in detail below), customer analytics (churn, NRR, cohort retention, payment regularity), compliance (six India-specific rules), and reconciliation (comparing the statement against whatever the company claims in its own materials, when that's supplied). A sixth component, the financial health alerts engine, sits slightly apart — it doesn't detect new things, it takes the outputs of the other analysts and classifies them into investor-relevant severity bands using one shared threshold table, so "NRR of 80%" or "runway of 3 months" gets the same severity label no matter which report you're reading.

**Layer 5 — Output.** Four report generators read the same set of analysis outputs and format them for their audience: a one-page PDF for an angel, a six-sheet workbook plus PDF for a VC, a ten-sheet workbench for a fund analyst (with room for fund-specific custom risk detectors bolted on without touching the core analysis code), and a cross-company comparison workbook for a network. None of them render an investment verdict or a star rating — that is a deliberate design choice, not an oversight: the tool's job is to surface evidence, counts, and quantified findings; the judgment about whether a specific company is investable belongs to the human reading the report, not to the tool.

## 4. What makes it trustworthy

Three design choices underpin whatever confidence someone can place in a BSAA report. The first is **deterministic-first**: wherever a finding can be computed with arithmetic or pattern matching, it is — burn rate, runway, the six risk detectors, the customer analytics metrics, and five of six compliance rules' triggering logic are all plain code with no model in the loop. Language models are used narrowly, for the things code genuinely can't do well: turning a list of flags into readable prose, fuzzy-matching a name variation, or categorising the rare transaction description that doesn't match any rule. Every LLM call has a rule-based or deterministic fallback, so the system degrades gracefully rather than breaking when an API key isn't configured or a call fails.

The second is **validation gating**. Bad input data — a statement whose running balance doesn't add up, which usually means an extraction error or, more rarely, a doctored document — genuinely stops the pipeline before any analysis runs on it. This sounds obvious, but it's worth being explicit that it's actually wired up end to end (both the demo pipeline and the standalone orchestrator check the validator's result and raise rather than continue), because a validator that computes a status nobody checks is a subtle and common failure mode in exactly this kind of system.

The third is **traceability**. Every transaction carries a `SourceReference` back to the exact page and row it came from in the original file, and every pipeline run is tagged with the schema version and the semver of every agent involved, persisted so a past run can be replayed under today's code and diffed against its original result. If a report says a company received four suspicious near-threshold cash deposits, that claim traces back to four specific rows in a specific PDF page, not a black box.

## 5. Customer analytics — capability and honest limits

Churn, net revenue retention, and cohort retention are the metrics that differentiate a SaaS-aware diligence tool from a generic transaction categoriser, and they only work because the Customer Identity Resolver upstream can tell customers apart. NRR here is computed as a straightforward period-over-period ratio — the same cohort's revenue this month versus last month — deliberately *not* annualised by raising a single month's ratio to the twelfth power, which would turn one noisy month into a wildly misleading full-year figure. Churn is detected conservatively: a customer only counts as churned once three full months of confirmed silence have passed, which is more reliable than guessing at churn from a single missed payment but means the metric structurally cannot produce anything meaningful on a statement shorter than about four months — a real limit worth knowing before requesting a 3-month statement window and expecting a churn number back.

The most important honest caveat is aggregator dominance. When a meaningful share of a company's revenue arrives as payment-gateway settlements rather than named counterparties, individual customers are genuinely invisible in bank data — no amount of clever clustering recovers who actually paid. Rather than pretend otherwise, the system tracks what share of revenue is aggregator-settled and surfaces an explicit warning on every report once that share crosses roughly a third of revenue: the customer analytics in that report should be read as partial, not complete. And because the entire 22-statement gold set used to measure this pipeline's accuracy is synthetically generated by the project's own generator — no real, anonymised bank statement has been run through it yet — the honest position is that these are prototype-stage accuracy numbers, not production-validated ones. On the current gold set, extraction and categorisation both measure in the high nineties, but risk-flag recall (73%) and customer-ID clustering accuracy (82%) both currently fall short of their own internal targets, which is exactly the kind of gap that matters more once real statements are in the mix.

## 6. Indian compliance handling

The compliance module checks a statement against six India-specific rules — cash receipt limits under §269ST, GST payment consistency, TDS disbursement patterns, PMLA cash-aggregation thresholds, related-party transaction concentration, and the §269SS/§269T cash loan prohibition — each carrying its exact statutory citation. The framing throughout is deliberately investor-risk language, not legal-compliance language: a flagged exception describes what an investor should worry about (a contingent tax liability, a penalty exposure, a governance question worth asking) rather than asserting that the company has definitively broken the law. Several of the rules go further and say so explicitly in their own description text — the GST, PMLA, and related-party rules are each labelled in the code as "a heuristic, not a statutory determination," precisely because a bank statement alone can't establish some of the facts (net worth, board approvals, filing status) that a real legal determination would require. This is the correct posture for a prototype: useful, quantified signal for a human due-diligence process, not a substitute for legal review, and anyone taking this into production should have counsel validate the rule thresholds and framing before relying on them as anything more than a first-pass flag.

## 7. Current status

As of this writing, BSAA is a working prototype covering four sprints of planned scope: the full five-layer pipeline runs end to end on HDFC and ICICI digital PDFs, plus bank-agnostic CSV, Excel, scanned-PDF, and image inputs; all four report lenses generate correctly; batch processing and run-versioning/replay both work; and the unit test suite (909 tests) passes at 908/909, with the one failure being a byte-length flake in a workbook-idempotency test rather than a functional defect.

What's explicitly still ahead, in rough order of what would matter most before anyone relies on this for a real investment decision: validating accuracy against real, anonymised bank statements rather than only the project's own synthetic gold set (the honest current gap, and the single biggest thing standing between "promising prototype" and "trusted tool"); closing the risk-recall and customer-ID-clustering gaps the regression suite is already catching; legal review of the six compliance rules' thresholds and framing before anyone treats them as more than a first-pass heuristic; broader bank coverage for the PDF path beyond HDFC and ICICI, ideally via a real profile system rather than more hardcoded per-bank logic; and, further out, production integration with India's Account Aggregator framework so statements can be pulled with consent rather than uploaded by hand. None of this is hidden risk — it's the deliberate, visible boundary of a solo eight-week build, and the architecture (deterministic-first, validation-gated, one engine behind four lenses) is built so that closing each of these gaps is additive work, not a rewrite.
